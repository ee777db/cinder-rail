# Cinder 原生协议白皮书

**版本：0.2 · 技术核验日期：2026-10-05（America/New_York）**

**Cinder 是一个采用 ML-DSA 签名的原生支付开发网。**它把代理服务付费、有限资源权益、音乐付费访问及精确分账放在同一套整数账本中，并提供可重放的交易记录。CINDER 是该账本自行发行的原生测试资产；WORK 是向当前运营者兑换一种明确计算服务的有限权益。

当前网络由单一运营者运行在 Cloudflare Workers 与 Durable Objects 上。它不是 PoW 网络，也没有独立验证者组成的 PoS / BFT 共识。运营者签署检查点、处理服务和保管状态。用户可以核对一份历史是否符合授权与守恒规则，但不能仅凭这份历史证明不存在另一份历史、运营者不会停机、或任意模型正确执行。

本文以仓库中的实际 v0.2 原生实现为范围。源码、接口、测试和运行报告是不同层次的证据；部署版本与运行结果应以对应发布记录为准。本文没有设定 CINDER 的美元价格、现金赎回、上市、股息或主网兑换承诺，也不把尚未实现的能力写成现有产品。

## 1. 要解决的具体问题

代理和创作者交易的困难不只是“转一笔币”。一次完整交易需要回答：谁有权花钱，最多花多少，买的是什么，结果如何绑定请求，失败后钱在哪，同一请求重试是否再次收费，以及收益怎样分给多个参与者。

不同系统分别记录这些信息时，付款、服务调用和业务账单容易脱节。Cinder 选择一个有限指令集，将这些关系显式化：

1. 所有支出由账户或有界会话密钥授权。
2. 金额使用整数原子，禁止浮点累计。
3. 每次账本变动对应已验证的动作和可检查的借贷记录。
4. 对异步服务先预留，再结算或退款；对可同步完成的资源兑换，先完成计算再提交消耗记录。
5. 收据说明它提供哪一类证据，不把签名、真实性、人格和执行正确性混为一谈。

产品要证明的是这些约束能降低集成与核账成本。原生币本身不是对需求、价格或安全的证明。

### 1.1 已有市场并非空白

机器支付、资源代币和代理商业已经有实际方案。x402 v2 定义支付请求、授权、验证与结算，包含 `exact`、`upto`、`batch-settlement` 等方案；Virtuals ACP 提供代理间约定、托管、交付和评估；Venice 允许锁定 sVVV 铸造 DIEM，并通过 DIEM 获得每日 API 额度。[x402 v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)、[ACP](https://os.virtuals.io/acp/overview)、[Venice 当前机制](https://venice.ai/faqs/all)

因此 Cinder 不宣称发明了机器支付、资源权益或批量结算。其现阶段实验是：**在自行定义的原生状态机上，从第一种交易格式起强制使用抗量子授权，并将预算、资源消耗和创作者分账放入可重放记录。**是否比已有组合更好，须比较同等任务下的集成成本、错误恢复和完整交易费用。

### 1.2 为什么当前选择原生账本

现有链能提供流动性、钱包、独立验证和合约生态；这些都是 Cinder 尚不具备的优势。选择独立账本，让本版可以直接控制签名格式、动作权限、整数资产规则与检查点结构，避免把 ML-DSA 账户假定成已有 EVM 钱包。代价是自身承担托管、分发、互操作、安全审查和未来共识建设。

当前托管设计适合验证有界状态机和应用流程，不构成“比 Ethereum、Solana 或其他网络更去中心化”的比较。大型网络也在推进密码迁移，例如 Ethereum 已公开其执行层、共识层和数据层的抗量子工作。[Ethereum PQ 项目](https://pq.ethereum.org/)

## 2. 当前实现与资产身份

| 层 | 当前实现 | 边界 |
| --- | --- | --- |
| 网络标识 | `cinder-devnet-1` | 一个托管原生开发网，不是主网 |
| CINDER | 原生余额、转账、费用、托管与应用支付 | 不是 ERC-20，也不是 USDC 或美元债权 |

| 执行与存储 | Worker 请求入口、单一原生 Durable Object、序列化状态提交 | 运营者和托管平台控制可用性及排序 |
| 计算 | SHA-384；固定配置的 Meta Llama 调用 | 哈希可重算；Llama 没有执行正确性证明 |
| 音乐 | 签名上传、不可变定价分账、付费访问、私有访问令牌 | 没有真人收听或版权真实性证明 |

## 3. CINDER 的发行、计价与守恒

### 3.1 创世发行

一枚 CINDER 等于 **1,000,000 atoms**，精度为六位小数。创世总量为：

`S = 1,000,000 CINDER = 1,000,000,000,000 atoms`

初始全部进入 `system:reserve`。费用、供应方和后续托管账户从零开始。注册账户初始余额为零；用户签署独立水龙头动作后，可从储备领取一次 **100 CINDER = 100,000,000 atoms**，水龙头动作不收费。

这是一笔储备转移，不是每注册一个账户就增发。现有用户动作没有铸造额外 CINDER 的能力。费用进入 `system:fees`，服务收入进入对应供应方账户，均仍属于总供应；本版不销毁 CINDER，不提供挖矿、质押收益或自动分红。代码也没有把系统收入账户当作普通用户钱包供人提取的公钥路径。

“每账户一次”不等于“每真人一次”。公钥可以批量生成，因此账户、IP 和每日配额只是开发网成本控制，不是人格验证。当前最多注册 5,000 个原生账户，实际可领取数量还受储备、容量及限流约束。测试分配不自动赋予未来主网份额。

### 3.2 金额表示与账本不变量

金额在签名消息中采用规范十进制整数字符串，例如 `"100"`，不接受指数、负数、前导零、浮点数或超出范围的值；计算使用 `BigInt`。动作所涉及账户不能出现负余额。

对每条记录的所有原生记账项 `δᵢ`：

`Σ δᵢ = 0`

从创世开始完整重放，还应有：

`Σ balance(account) = S`

总量包括储备、用户、费用、供应方、市场池和所有托管账户。把账户总额相加而漏掉 escrow，会错误地得出“币丢失”；把系统费用称为烧毁，会错误地得出“供应通缩”。

普通收款人必须预先注册。特殊 `system:` 账户不能作为任意用户地址使用，避免把直接转账混入池储备等独立会计规则。

### 3.3 费用

| 操作 | 原生手续费 | 服务本金或其他费用 |
| --- | --- | --- |
| 单独水龙头 | 0 | 储备向用户转 100 CINDER |
| 普通含 `m` 个动作的批次 | `10 + 2m` atoms，`1 ≤ m ≤ 16` | 转账或分账金额另计 |
| 独立 SHA-384 计算 | 12 atoms | 100 atoms 先托管 |
| 独立 Llama 推理 | 12 atoms | 500 atoms 先托管 |
| 音乐发布、下架 | 各 12 atoms | 无额外协议设定费用 |
| 音乐付费访问 | 12 atoms | 曲目固定价格另计并精确分账 |
| 每个 WORK / 市场动作 | 12 atoms | 购买、交换或提供流动性的金额另计 |
| 通道开通 | 12 atoms | `capacity × 100` atoms 抵押 |
| 通道每次调用 | 0 额外原生手续费 | 消耗 100 atoms 的抵押权益，待关闭记账 |
| 所有人主动关闭通道 | 12 atoms | 已用结算、未用退回 |
| 到期系统关闭 | 0 | 同样结算及退款 |
| 市场 swap | 上述 12 atoms | 30 bps 交易费留在池内 |

单动作 12 atoms 是 **0.000012 CINDER**，不是 0.000012 美元。没有可信外部价格时，本协议不能将其宣传为“低于一美分”。原生币固定供给和服务固定币价也不会使购买力稳定。

## 4. 账户、规范编码与签名授权

### 4.1 账户不是人格

账户地址为 `cin1` 加上公钥原始字节的完整 SHA-384 十六进制摘要，共保留 384 位承诺。`cin1` 只是前缀，**不是 Bech32 校验码**。注册要求提交公钥和对应私钥签署的账户注册证明。

拥有私钥只证明对该密钥的控制。账户可以由一个人、一个组织、多个进程或一个代理操作；它不证明独特真人、法律身份、版权或模型能力。DID 等身份标准可描述控制者和验证方法，但也不自动提供这些额外事实。[W3C DID Core](https://www.w3.org/TR/did/)

本版没有链上换钥、社会恢复、硬件钱包集成或多人审批。丢失私钥后，没有仅凭用户名重置原生账户的路径。

### 4.2 受限 JSON 规范编码

签名和哈希使用同一个编码函数：递归排序对象字段，按 JavaScript UTF-16 顺序排列键，保留字符串的精确 Unicode 内容，不做正规化。允许 `null`、布尔、字符串、安全整数、稠密数组和普通对象；拒绝负零、非整数、孤立代理项、循环引用、getter、非普通对象和稀疏数组。

编码上限为 65,536 UTF-8 字节、64 层深度和 20,000 个节点；HTTP 原生提交入口另有更紧的 **48,000 字节**请求上限。公钥与签名使用严格、无 padding 的规范 base64url，解码后的字节数必须精确匹配。

这是一套 Cinder 的受限 JSON 规则，不宣称完整实现 RFC 8785。任何其他语言 SDK 都必须匹配字段排序、整数和 Unicode 语义，不能用“普通 JSON 序列化通常一样”代替跨实现向量测试。[密码及编码源码](../src/native-crypto.ts)

### 4.3 交易信封

普通原生交易必须精确包含：

```json
{
  "domain": "cinder.transaction.v1",
  "chainId": "cinder-devnet-1",
  "sender": "<原生地址>",
  "nonce": 1,
  "validUntil": "<规范 ISO 时间，未来五分钟内>",
  "maxDebitAtoms": "112",
  "actions": [
    {"type": "compute", "service": "hash", "inputHash": "<96 位小写十六进制>"}
  ]
}
```

签名覆盖整个信封。`nonce` 必须恰好为账户上一个已接受 nonce 加一；`validUntil` 在接收及最终追加检查点时仍须有效；未知或缺少字段被拒绝。计算、音乐、资源市场和通道开闭各使用独立单动作交易，普通转账及分账才可按规则批量。

`maxDebitAtoms` 是**总支出上限**，包括网络费用及动作需要的完整本金。不能因为付款人也是分账接收者，就先净额化再绕过上限。WORK 输入、赎回或撤出流动性也要求用户事先持有 12 atoms 支付费用，不能先用尚未完成的交换所得垫付这笔费用。

`chainId` 和 `domain` 防止不同网络或不同消息类型之间混用，但本版信封没有另绑定创世摘要。同一个 `chainId` 不应被重置后当成同一个可信网络继续使用；发行新创世应使用新网络标识，并由客户端重新核验信任根。

### 4.4 重试与幂等

交易 ID 是规范交易信封的 SHA-384，不包括签名字节。ML-DSA 使用新随机性时，同一授权可能有不同有效签名；仍对应同一个交易 ID。

服务器保存成功交易。完全相同的授权重试时，仍重新验证签名，再返回既有收据，不再次扣款或推进 nonce。已接受交易即使后来过期，也可走这个认证后的重放路径；这不允许接受新的过期交易。网络超时之后应查询或重发原授权，而不是立即创建一个新 nonce 的替代付款。

SDK 的 `submit()` 还核对原授权、交易编号、收据内容承诺、总借方支出上限及记账守恒。`job()` 会取得原计算预留收据，验证付款公钥与地址的绑定及用户签名，重算预留，再核对终态的域、网络、请求、服务、模型、输出、退款和实际付款对象。声称 complete / failed 却缺少结算收据的响应被拒绝；未知状态或不符协议的结算域也被拒绝。这些检查不代替从创世重放历史余额。

同一个 SDK 实例会保留未确认的通道开通授权及会话密钥，重试原参数时继续原请求；并发相同开通也共用一次授权。音乐 `listen()` 保留原付款授权，付款成功而取播放权限失败时，重试只恢复权限。错误中的 `pendingTransactionHash` 可用于核对；音乐错误还带有原 `authorization`，便于保存并恢复。此状态只在进程内存中，刷新或退出不保证保留。应用仍须安全保存待确认授权、通道私钥和已确认交易编号，不能将“没有收到响应”当作“没有付款”。

## 5. 抗量子安全的精确范围

### 5.1 使用的原语

原生账户、通道会话和运营者检查点使用 **ML-DSA-65**。协议调用标准化的 Pure ML-DSA 签名，不是 HashML-DSA；固定签名 context 为 `cinder-native-v1`，消息内部另有 domain、chainId 及相应授权字段。

| 原语或数据 | 当前尺寸 / 方式 |
| --- | --- |
| ML-DSA-65 公钥 | 1,952 字节 |
| 展开私钥 | 4,032 字节 |
| 签名 | 3,309 字节 |
| SHA-384 摘要 | 48 字节，显示为 96 位十六进制 |
| 随机源 | 浏览器或 Worker 的 `crypto.getRandomValues` |
| 签名实现 | `@noble/post-quantum` 0.7.1 |
| 哈希实现 | `@noble/hashes` 2.4.0 |

ML-DSA 是 NIST FIPS 204 定义的数字签名标准；采用标准参数不表示本软件获得 FIPS 实现认证。NIST 发布页也列有潜在修正说明，依赖与测试向量需要持续跟踪。[FIPS 204](https://csrc.nist.gov/pubs/fips/204/final)、[标准原文](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.204.pdf)

### 5.2 量子威胁与不应作出的推断

Shor 算法对整数分解和离散对数提供量子算法，威胁 RSA、椭圆曲线等现有公钥体系；Grover 的通用搜索加速是平方级，并不意味着所有哈希立即失效。理想化 384 位哈希的通用量子原像搜索约为 `2^192` 查询；通用量子碰撞算法的查询级别约为 `2^128`。查询复杂度不是现实机器运行时间或攻破年份预测。[Shor](https://arxiv.org/abs/quant-ph/9508027)、[Grover](https://arxiv.org/abs/quant-ph/9605043)、[量子碰撞算法](https://arxiv.org/abs/quant-ph/9705002)

本版的签名设计避免以椭圆曲线账户作为原生授权根；通道会话也使用 ML-DSA。但以下事项没有被算法选择自动解决：

- JavaScript 引擎的时序、内存复制、浏览器扩展、恶意依赖和随机数环境。
- 运营者账户、发布权限、服务端私钥存储、备份和数据库访问。
- TLS 的证书认证、内部连接及托管控制面。
- 人格、法律授权、内容权属、外部服务是否真的按承诺执行。
- 未来算法迁移、运营者换钥和用户密钥恢复流程。

所固定的 noble 版本明确区分自审与独立审计，并不宣称 JavaScript 签名为常数时间。因此本文使用“原生交易采用标准化抗量子签名”，不使用“系统全面量子安全”或“永远无法破解”。[固定版本安全说明](https://github.com/paulmillr/noble-post-quantum/tree/0.7.1#security)

Cloudflare 也区分后量子密钥协商与证书认证。即使某段连接采用混合密钥协商，也不能推导出所有连接、部署权限和应用均完成抗量子迁移。[Cloudflare PQ 边界](https://developers.cloudflare.com/ssl/post-quantum-cryptography/)

### 5.3 钱包备份

浏览器原生钱包使用内存中的密钥；加密备份文件在本地生成。当前备份使用 PBKDF2-SHA-384、310,000 次迭代、32 字节随机盐，以及 AES-256-GCM、12 字节随机 IV、128 位认证标签。备份头部作为附加认证数据；解密后检查网络、公钥地址及私钥对应关系。

密码至少 12 个字符只是格式下限，不保证高熵。加密文件泄露后，弱密码仍可被离线尝试。私钥和明文缓冲的清零只是尽力而为，JavaScript 字符串及引擎副本无法保证擦除。当前服务没有密码找回功能；会话中的明文密钥也不是硬件隔离密钥。[钱包备份实现](../browser/wallet-vault.ts)

## 6. 执行、持久化和检查点

### 6.1 单一原生执行器

网络入口将原生请求交给以 `cinder-devnet-1` 命名的一个 Durable Object。状态相关处理放在 `blockConcurrencyWhile` 内，防止同一状态上的请求交错提交。纯状态转换模块先对快照计算新状态；异常不提交这些余额或 nonce 变化。

成功时，账户、业务状态、去重项、收据及链头通过同一个存储批次提交。Cloudflare 的存储事务与输出门提供宿主层持久化语义；这些是托管平台保证，不是跨独立验证者的共识。[Durable Object 存储](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

“失败不扣款”指业务状态转换未提交。请求限流计数可能在业务验证之前更新，恶意或失败请求仍可消耗配额。HTTP 响应丢失也不证明提交失败；必须使用既有交易 ID 恢复。

### 6.2 检查点承诺什么

每个全局检查点包含：

```text
domain, chainId, height, previousHash,
transactionHash, postingsHash, resultHash,
timestamp, mode = single-operator-devnet
```

运营者对检查点签名；检查点哈希成为下一条的 `previousHash`。完整收据包含原始交易、用户签名、检查点及运营者签名、原生记账项和业务结果。创世记录另外承诺供应、初始分配、运营者公钥及资源定义。

这不是对整个数据库建立的 Merkle 状态根，也没有独立时间戳机构。高度和时间由运营者提供；审计器检查顺序和哈希链接。时间失准、数据回滚或分叉需要额外运营及外部观察机制处理。

### 6.3 独立重放能发现什么

审计工具从可信创世开始，验证：

1. 创世和每条检查点的签名、连续高度及前向链接。
2. 交易、记账项和结果摘要与收据内容一致。
3. 公钥确实派生出声明的账户地址，用户授权有效。
4. 公开状态机重算的 nonce、费用、金额和业务结果匹配收据。
5. 所有原生余额非负，供应守恒；WORK、LP 和池储备可调和。
6. 通道关闭所承诺的全部授权日志可取得，签名、序号、链接和金额一致。

只验运营者签名，无法发现一条“签得正确但业务规则错误”的收据；所以工具还会重跑转换逻辑。[审计入口](../scripts/audit-native.mjs)、[重放器](../scripts/lib/ledger-replay.mjs)

默认从同一服务器下载公钥属于首次信任。审计命令支持显式 `CINDER_OPERATOR_KEY` 固定可信公钥，使用者还应保留创世摘要及既有链头。固定密钥能发现无说明的换钥；却不能阻止同一个运营者用同一个密钥签两份各自有效的分叉。独立观察者、外部透明日志与数据可用性机制尚未部署。

审计器只能检查获得的历史，不能强迫服务器给出遗漏数据，也不能证明其未拒绝特定用户。原生余额状态可验证与网络无需信任，是两个不同结论。

## 7. 计算支付与失败恢复

### 7.1 独立计算请求

用户签署 `compute` 动作，绑定服务和输入 SHA-384，原始输入单独提交。运营者先检查精确输入与长度，再将服务价格转入 `system:escrow:<transactionHash>`，费用进入费用账户，并记录 pending job。

当前两个独立服务为：

| 服务 | 输入上限 | 服务价 | 执行 |
| --- | --- | --- | --- |
| `hash` | 1–4,000 UTF-16 code units，必须是合法 Unicode | 100 atoms | 对精确 UTF-8 输入计算 SHA-384 |
| `inference` | 1–1,200 UTF-16 code units | 500 atoms | Cloudflare Workers AI，`@cf/meta/llama-3.1-8b-instruct-fp8-fast` |

模型请求当前限制 `max_tokens: 192`、`temperature: 0.2`，并带有简短回答的系统提示。具体服务配置属于运营者声明；它不是对权重、tokenizer 或硬件执行的密码学承诺。

### 7.2 结算状态机

```text
已验证授权
    → 托管 + pending（原子提交）
    → 输出在两分钟租约内完成 → 托管付供应方 + complete
    → 执行失败 / 租约到期      → 托管退付款人 + failed
```

只有 pending job 能结算，托管余额必须等于原始服务金额。结算创建新的系统交易及运营者检查点，原子写入余额、job 结果和 pending 列表。超过两分钟才到达的输出不再收取服务本金；失败退款不退已经支付的原生网络手续费。

恢复闹钟在预留提交前设置；如果设置失败，不提交这次余额和 nonce 变化。闹钟、部分查询和已接受交易重试都会触发到期恢复。原始推理输入没有作为 job 重放材料长期存储，系统不会在中断后自动重新执行一次外部推理，以免产生不明重复成本。

闹钟可以延迟执行，托管平台不可用时退款也可能延迟；两分钟是接受成功输出的代码判定边界，不是对互联网或云平台的退款到账时限保证。[Durable Object alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)、[恢复测试](../tests/native-recovery.test.mjs)

### 7.3 当前证明等级

SHA-384 服务可由客户端独立重算。但是客户端提交时已计算输入摘要，返回值正是同一个摘要；它是一项便于审计支付闭环的最小工作负载，并不为客户端提供新知识，也不证明消耗了多少能源或在哪台机器运行。

Llama 收据绑定输入承诺、输出、输出摘要、服务和声明的模型。签名证明运营者承担该声明；哈希证明输出内容一致。**两者都不证明指定模型按指定权重执行，更不证明回答正确。**

## 8. 预付资源通道

### 8.1 有界授权

所有人用账户密钥签署通道开通动作，指定不同于账户公钥的 ML-DSA 会话公钥、`hash` 服务、1–10,000 次容量，以及不超过未来 24 小时的到期时间。通道 ID 等于开通交易哈希。

容量为 `C` 时预留 `D = 100C` atoms，并另付 12 atoms。开通检查点承诺价格、服务、会话公钥、容量、到期时间和初始日志头。会话密钥只能授权这个通道内的调用，不能转走所有人其余余额、改变价格或关闭通道。被盗会话密钥仍可能耗尽该通道剩余额度。

主机另外为公开日志设置全网终身 **100,000 次调用**的存储预算。令 `A` 为已经接受的调用数、`R` 为所有未关闭通道尚未使用的容量，开通 `C` 次通道要求 `A + R + C ≤ 100,000`。开通预留 `C`，一次新调用令 `A += 1、R -= 1`，关闭释放未用的 `R`，已接受历史不会被重新释放；精确重试不改变计数。这项预算独立于 CINDER 托管、单通道上限和每日请求配额。

每次调用签署：

```text
{ domain: cinder.channel-call.v1,
  chainId, channelId, sequence, inputHash }
```

新调用要求精确的下一个序号、开放且未到期状态、有效会话签名、匹配输入，以及完整抵押仍存在。相同序号的不同输入拒绝；完全相同的既有调用经重新认证后返回原记录，不增加消费。关闭或过期之后仍可重取既有调用，不可接受新调用。

### 8.2 调用不偷偷改变全局余额

接受第 `n` 次调用后：

`spentAtoms = 100n`

`remainingAtoms = 100(C − n)`

但 escrow 账户余额仍是完整的 `100C`。调用阶段只原子更新通道状态与日志，不生成原生账户记账项，也不生成新的全局检查点。

日志包含授权、会话签名、消息摘要、序号、前一日志哈希、输入输出承诺、结果、金额和记录时间。每次调用没有额外运营者 ML-DSA 检查点签名；它的 HTTP 成功是**运营者对抵押支持授权的临时确认**。所有人签名的授权不等于供应方签名的履约证明。

这一区分保留了审计可重放性：未关闭前的供应方收入只是通道内应付权益，不应在全局余额中凭空增加。

### 8.3 关闭与费用摊销

主动关闭由所有人签名，另付 12 atoms，消耗一个所有人 nonce：

`escrow → provider：100n`

`escrow → owner：100(C − n)`

关闭不能取消已消费调用。到期后，系统执行相同分配，但不收关闭费、不要求所有人签名，也不推进所有人 nonce。这条路径减少对所有人在线或仍持有液态费用余额的依赖，但仍依赖运营者运行恢复程序。

关闭检查点承诺调用数、日志头、已用金额及退款；审计器需要取得全部日志验证，单独一个哈希不能替代数据可用性。重复关闭拒绝。

SDK 从经过验证的开通收据缓存不可变条款；新客户端可按通道 ID 取回开通交易，再验证运营者签名、所有人签名及金额。每次响应逐项检查授权、日志域、时间范围、固定价格、输出、零额外费、零已结算额，以及剩余抵押的整数运算。第一条日志必须链接开通头；后续条目核对调用方传入或此前缓存的前驱。断点恢复时应保留并传入前驱，或从头验证完整日志。未提供且未缓存前驱的单条响应不证明前面的历史；未经最终关闭承诺的记录也不证明运营者没有改写其他临时确认。

完成 `n > 0` 次并主动关闭时，平均成本是：

`100 + 24/n atoms/调用`

到期关闭时是 `100 + 12/n`。例如 10,000 次调用主动关闭，资源费用为 1,000,000 atoms，开闭费用总计 24 atoms，平均为 100.0024 atoms。这里没有把网络、签名、存储和 CPU 成本变成零，也没有美元换算。[通道接口](channel-interface.md)、[通道实现](../src/native-channel.ts)

## 9. WORK：有限的资源权益

### 9.1 单位定义

WORK 初始总量为 **1,000,000 个整数单位**，无小数位。每单位对应运营者对一个合法 Unicode 文本执行一次 SHA-384 的服务承诺，输入长度为 1–4,000 UTF-16 code units，哈希对象是精确 UTF-8 字节。

库存销售价格为每 WORK **100 CINDER atoms**。购买费另计。WORK 可转移、放入池、交换或兑换；没有用户增发动作。当前报价没有权益到期字段，不能据此推导出开发网永久在线或永久兑付保证。有限数量是软件发行边界，不是 GPU、服务器或能源储备的第三方审计。

在正常运行规则内：

`库存 + 用户持有 + 池中持有 + 已消耗 = 1,000,000`

兑换一次减少用户 1 WORK，增加已消耗 1 WORK，并支付 12 atoms 原生费。主机验证原始输入并完成同步哈希后，才把消耗与收据一起写入。这里不需要异步推理的预留状态；输入错误或执行未完成就不提交消耗。

### 9.2 与 CINDER 的关系

CINDER 是一般原生支付和费用资产；WORK 是特定供应方、特定服务的权益。WORK 成功兑换时被计为消耗，CINDER 购买款已经成为供应方账户余额。两者不能合并成“烧掉原生币产生计算”的描述。

WORK 不代表 Llama 推理额度，也不能从一次小文本哈希外推为通用 FLOPs。即使两台机器执行同样 FLOPs，不同内存、模型、精度、带宽和延迟仍可能提供不同服务质量。

Venice DIEM 提供按供应商价目计算的持续 API 美元额度；Cinder WORK 提供有限次数的窄服务。前者需要解释长期服务承诺，后者更容易界定最大资源义务，但不能因此宣称替代了前者的模型产品。[DIEM](https://venice.ai/blog/introducing-diem-as-tokenized-intelligence-the-next-evolution-of-vvv)、[WORK 接口](economy-interface.md)

## 10. CINDER / WORK 现货池

### 10.1 谁提供流动性

池初始没有 CINDER、WORK 或 LP 份额。第一个用户必须真实存入两种开发网资产，才能开始交易。系统不伪造深度、不自动向池注入创世储备，也没有美元储备。

以 `x` 表示池中 CINDER atoms，`y` 表示 WORK 单位，`L` 表示 LP 总份额。首次存入 `a` 与 `b` 时：

`新 LP = floor(sqrt(a × b))`

以后按两边最大可投入量铸造：

`m = min(floor(a × L/x), floor(b × L/y))`

实际收取 `ceil(m × x/L)` 和 `ceil(m × y/L)`，不超过用户签署的最大值，未用部分留在用户账户。按 LP 份额撤出时，两边分别向下取整；最后持有人撤出全部份额时清空储备。本版没有永久锁定最低 LP，也没有 LP 转账接口。

### 10.2 交换规则

输入资产数量为 `a`、输入储备为 `x`、输出储备为 `y`：

`out = floor(a × 9970 × y / (x × 10000 + a × 9970))`

完整输入进入池，30 bps 留在储备中，归池份额持有人共同承担和享有；每笔另外付 12 atoms 原生费。执行要求输出为正且低于储备，满足签署的 `minOut`、期限和余额条件，交换后 `x × y` 不下降。

算法借鉴既有常数乘积与比例份额机制；本实现是单运营者原生状态机，不是经审计的 Uniswap 合约部署。[Uniswap v2 白皮书](https://docs.uniswap.org/whitepaper.pdf)、[原始 Pair 合约](https://github.com/Uniswap/v2-core/blob/master/contracts/UniswapV2Pair.sol)

### 10.3 风险与价格

只读报价不锁定价格。`minOut` 限制可接受执行结果，却不保证公平排序、不消除价格操纵和薄流动性滑点。零小数 WORK 还会使小额交易出现明显离散化；输出为零的交易被拒绝。

运营者库存报价 100 atoms/WORK 与池报价属于两个机制。库存有限、费用存在、没有反向现金兑付，因此不能宣称无限套利把二级价格永久钉在 100。LP 面对两种资产相对价格变化和库存组成变化，不存在收益率保证。

池储备必须等于原生池持有账户的真实余额；WORK 与 LP 采用全局计数及分片钱包记录。普通操作仅加载相关分片，全量审计或历史重放才能检查完整分片集合。错误地漏读一个既有钱包不能靠总计字段神奇修复。[市场实现](../src/native-economy.ts)

## 11. 音乐发布、访问与分账

### 11.1 文件与不可变元数据

上传者先注册账户，再用账户密钥逐块授权上传。当前每块最多 24 KiB，文件为 12 字节至 4 MiB，允许 MPEG、WAV、Ogg。每块绑定 owner、uploadId、完整文件摘要、MIME、字节数、块数、序号、块摘要和未来 30 分钟内的期限。

块按顺序写入，已接受的块不能被不同内容替换；完成时重算整份原始音频字节的 SHA-384。主机仅作有限的文件头检查，不能由 MIME 或摘要推导音频一定安全、可解码或内容权利有效。

发布动作随后绑定文件摘要、标题、艺名、格式、长度、价格、收款人和明确的 `rightsDeclared: true`。主机确认文件已上传且 owner、摘要、类型和大小匹配。曲目 ID 包含 owner、发布 nonce 及不可变公开元数据承诺；价格或分账改变需要新发布。

权利声明是上传者自述。协议没有调查作品来源、版权合同或人类身份。下架停止新的付费访问，历史元数据和收据保留；它不等于删除所有文件副本。

### 11.2 精确分账

每首曲目有 1–8 个不同、已注册接收者，权重 `wᵢ` 为正整数基点且总和为 10,000。净曲目价格为 `P`：

`基础份额ᵢ = floor(P × wᵢ / 10000)`

剩余原子按小数余数从大到小分配；同余数以地址字典顺序决胜。因此 `Σ payoutᵢ = P`。101 atoms 按 70% / 20% / 10% 分配，结果为 **71、20、10**，另付 12 atoms 手续费。

付款人即使也是收款人，也必须先持有完整 `P + 12` 并签署相应上限。不能通过自收款循环制造余额或缩小授权总支出。

### 11.3 去重与私有播放权限

`music.listen` 接收曲目 ID 和 16 随机字节表示的 32 位十六进制 `listenId`。去重键绑定付款账户与 listenId，不依赖曲目；同一账户复用该 ID 即使换 nonce 或换曲目也拒绝。全新 ID 代表另一次主动购买，不代表另一个真人。

付款成功时，账本变动、访问记录和随机 256 位播放能力令牌一起提交。**令牌不会进入公开交易或付款重放响应。**付款人再签署一个五分钟内有效的 `cinder.music.playback.v1` 请求，绑定付款交易哈希，从 `/music/access` 取得原令牌。

该请求包含随机 nonce，但当前没有单独消费它的一次性 nonce 存储；应描述为短期有效签名证明，而非一次性挑战。拥有这份短期证明的人在其有效期内可能重新取得同一令牌。

令牌自付款时起有效一小时，媒体入口以 token 和音频哈希检查权限，并支持单段字节范围。令牌是 bearer capability：谁获得令牌，谁能在有效期内访问相应音频；它不是 DRM。合法用户能复制音频，令牌也可能被主动分享。已付窗口内的访问不因元数据下架自动撤销；文件不可用或令牌过期仍会失败。[音乐接口](music-interface.md)、[媒体实现](../src/native-media.ts)

**付费访问记录只证明付款及分配，不证明人听了、听了多久、喜欢作品，或上传者拥有版权。**机器人可以购买，创作者可以自费制造活动。本版不按自报播放数或分账动作的 `units` 额外铸币。

## 12. 隐私与信任边界

原生开发网是一份公开可读的支付历史。公开信息包括地址、公钥、余额与 nonce、交易、签名、记账项、曲目元数据、接收者和分配、通道状态及调用日志。计算成功结果也出现在 job 或收据中，尤其 **Llama 输出不是私有保存内容**。

原始计算输入为请求执行所需，会到达运营者；Llama 输入进一步发送给 Cloudflare Workers AI。当前原生 job 不保存原始输入用于重新执行，但这不等于端到端加密，也不排除托管层处理网络数据。输入哈希对低熵内容可被字典猜测，不是秘密隐藏工具。

音频保存于运营者存储，公开摘要不直接授予访问，但运营者有能力读取文件和播放令牌。本版没有客户端内容端到端加密或独立的权限托管方。

限流使用每日盐与 IP 的哈希，记录每日轮换；应用配置关闭 observability 日志，不代表托管提供方绝不处理 IP 或基础设施日志。原生账本、结果、曲目和媒体当前没有实现定时删除机制。旧沙盒的 24 小时会话期限**不能用于描述原生数据保留**。

| 对手或故障 | 当前控制 | 剩余信任与限制 |
| --- | --- | --- |
| 网络重试或恶意重复请求 | 交易哈希、nonce、listenId、通道序号去重 | 丢失数据库去重记录会破坏假设；需保留历史 |
| 无权付款者 | ML-DSA 验签、域隔离、预算和期限 | 私钥或前端被攻破可授权真实损失 |
| 会话密钥窃取 | 仅指定通道、服务、容量、期限 | 可消耗该通道剩余额度 |
| 恶意上传或刷量 | 大小、格式、账户及每日配额 | 不是内容审核、版权验证或反女巫证明 |
| 运营者错误记账 | 签名记录、整数守恒、独立重放 | 运营者仍可拒绝服务、删数据或签分叉 |
| 供应方错误输出 | 窄哈希可重算；输出内容承诺 | Llama 没有执行证明；回答真伪另行判断 |
| 托管中断 | pending 租约、闹钟、认证重试恢复 | 持续不可用时不能保证实时退款或退出 |
| 数据与身份泄漏 | 原始输入不作为 job 长期重放资料，媒体令牌私有返回 | 公开交易可关联账户；输出、文件和令牌仍信任运营者 |

## 13. 接口与运行边界

以下均相对 `/api/native`，网络签名格式不是 x402 wire format。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /info`、`GET /genesis` | 网络配置、当前链头、创世和运营者公钥 |
| `POST /accounts` | 以公钥和签名证明注册 |
| `GET /accounts/:address` | 查询公开原生账户 |
| `POST /submit` | 提交签名原生交易；异步计算可返回 202 |
| `GET /transactions/:hash`、`GET /jobs/:hash` | 获取既有收据或计算状态 |
| `GET /blocks?after=height`、`GET /export?after=height` | 分页检查点或完整重放资料，每页最多 20 条 |
| `GET /economy?address=...` | 库存、池和指定资源钱包 |
| `POST /media/upload` | 上传签名音频块 |
| `GET /music/catalog?after=trackId`、`GET /music/tracks/:id` | 分页曲目或曲目详情 |
| `POST /music/access` | 付款人签署短期证明后取播放令牌 |
| `GET /media/:audioHash?token=...` | 以能力令牌读取音频，支持 Range |
| `POST /channels/call` | 会话密钥授权的通道调用 |
| `GET /channels/:id`、`GET /channels/:id/journal?after=sequence` | 通道状态及分页日志 |

目录分页按存储曲目键排序，先取最多 20 条再过滤已下架项；页面可能不足 20 首而仍有下一页。公开报价和状态查询不预留资产，也不是新的支出授权。错误状态包括格式或动作校验、401/403 权限问题、409 状态冲突、410 过期、429 配额及服务容量错误；具体调用应以 SDK 和返回错误码处理。[SDK](../sdk/native-client.ts)

### 13.1 不是无限扩展网络

| 界限 | 当前代码值 |
| --- | --- |
| 原生注册账户 | 5,000 |
| 新普通交易停止接收高度 | 已有高度达到 9,900 时；所有人关闭通道属于恢复例外 |
| 全局检查点总容量 | 10,000，最后 100 条留给计算结算、通道到期和所有人关闭 |
| 独立 pending compute | 最多 10 个，租约 120 秒 |
| 未关闭通道 | 最多 32 个 |
| 单通道 | 最多 10,000 次，最长 24 小时 |
| 全网终身通道日志预算 | 已接受调用加未使用预留最多 100,000 次；关闭释放未用预留 |
| 音频上传 | 全网终身 200 份、每账户 10 份 |
| 曲目发布 | 全网终身 200 次、每账户 10 次，下架不释放名额 |
| 资源钱包 | 最多 5,000 个；清零不删除已初始化计数 |
| WORK 单账户 | 最多 100,000 单位 |
| WORK 单次输入 | 购买、转移、提供流动性、交换最多 10,000 单位 |
| 市场 / 购买单次 CINDER 输入 | 最多 1,000,000,000 atoms，即 1,000 CINDER |
| HTTP POST | 48,000 字节 |

代码还设置每日全网及每 IP 配额：普通读取 50,000 / 1,800，历史导出与通道日志读取 100,000 / 20,000，普通写入 10,000 / 300，注册 500 / 20，上传块 20,000 / 2,000，通道调用 500,000 / 250,000；原生推理全网每天最多 30 次，每日最多记录 2,048 个限流客户端。历史读取使用独立配额，避免普通页面查询直接耗尽审计预算。配额计数包含请求尝试和重试，不能代替更紧的终身成功调用预算，也不应理解为成功服务数量承诺。`/info.limits` 公布检查点上限、累计接受、未用预留及当前可预留调用数。

这些参数是当前发布的运营限制，不是性能基准。它们可以拒绝新的工作，也会限制读取与恢复请求；运营者须监测剩余容量。普通交易达到 9,900 高度后，所有人主动关闭通道和系统到期结算仍可使用保留空间，但不得超过 10,000 总上限。当前没有用户自己运行完整节点接管服务、越过停机取回资产的退出路径。

## 15. 从开发网到更强保证，需要分别完成什么

### 15.1 经济可持续性

资源单位须有真实可交付服务。对某种工作：

`服务收入 ≥ 执行 + 验证 + 带宽/存储 + 重试 + 运营 + 风险准备`

发币、锁仓或销毁不提供免费的计算资源。固定 CINDER 报价 `q` 在外部价格 `p(t)` 下的美元成本是 `q × p(t)`；如要固定美元预算，必须另处理可靠价格来源、兑换、滑点和库存。没有这些条件时继续以原生单位报价。

手续费首先是提供服务的收入去向问题，不能一边将同一笔钱写成“全部销毁”，一边又拿它支付运营和奖励。Lido 的 NEST 把回购放在累计盈余条件之后，是不同于无限补贴的设计参考；并不意味着 Cinder 已启用相同机制。[NEST](https://blog.lido.fi/ldo-automated-buybacks-overview/)

### 15.2 独立共识与可用性

若转向开放网络，需要独立故障域的验证者、成员与权重规则、可验证区块、锁定及投票轮次、冲突证据、数据可用性、同步与恢复、升级和密钥轮换。PoS + BFT 是可研究方向，但“三分之二签名”本身不是完整安全协议；验证者集中或由同一个运营者控制，不会变成独立共识。

还须解决较大的 ML-DSA 公钥与签名如何影响带宽、存储和验证。当前通道摊销了检查点费用，却仍保留每次 3,309 字节授权签名；不能宣称已经有抗量子聚合签名或压缩证明。本版没有 BLS 聚合，也没有后量子共识实现。

### 15.3 更强计算证据

不同证据回答不同问题，不能简单排列成一个万能“可信等级”：

| 方式 | 需要增加的系统 | 仍然不能证明 |
| --- | --- | --- |
| 独立重算 | 明确函数、输入和一致的数值语义 | 运行地点、耗能、答案的社会意义 |
| TEE 证明 | 硬件证明链、测量策略、新鲜挑战、撤销及补丁状态，绑定请求与结果密钥 | 获准程序没有业务错误、答案真实、供应商永不失守 |
| 乐观争议 | 可用执行轨迹、诚实挑战者激励、确定性和可执行处罚 | 无人监督也安全、即时最终接受 |
| ZK / 有效计算证明 | 精确模型与数值关系、证明器、验证器、实现审计及成本测量 | 模型结论符合现实、所有证明系统自动抗量子 |

TEE 依赖其硬件及软件可信计算基；ZKML 证明需要明确量化、近似、权重和采样关系；乐观模型还要处理隐私输入与挑战者可重放之间的冲突。当前 Llama 路径没有返回这些证据，不能由托管供应商名称推断已有 TEE / ZK 验证。[Intel 证明与可信计算基](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/trusted-computing-base-recovery.html)、[zkLLM 研究](https://arxiv.org/abs/2404.16109)、[opML 研究](https://arxiv.org/abs/2401.17555)

### 15.4 应用采用与硬件现实

音乐业务还需要真实授权内容、争议与下架流程、服务可用性及创作者复购。代理计算还需要明确供应商、资源版本、可靠预算和失败策略。市场业务需要实际参与者和流动性，不能把自测交易当成外部需求。硬件安全钱包、浏览器或移动设备上的签名体验、TEE 服务以及跨平台 SDK，都需要真实设备与独立集成验证。

当前没有一个链上听歌事件能证明人类关注，没有一个自有币能自动带来市场深度，也没有一个后量子算法名能替代部署和运营安全。后续发布应继续按能力逐项给出实现、测试和运行证据，使用户清楚知道自己收到的究竟是授权、交付、结算还是额外的独立证明。
